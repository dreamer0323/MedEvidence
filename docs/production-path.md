## 0. 一句话结论

**表结构不用改；要改的是「部署形态」和「运维四件事」。**

迁移成本 = **1 个常量**（`MILVUS_URI`）+ **5 项运维** + **1 项索引策略** + **1 处真代码改动**（应用不能假设"库在本进程里"）。

说"迁 standalone 要大改表"会被懂 Milvus 的人当场戳穿 —— 它的 schema / API 在 Lite 和 standalone 上完全一致。

## 1. 现在这套的真实形态

```
FastAPI / CLI
    │  进程内，无网络
    ▼
pymilvus 自动拉起 Lite 服务（127.0.0.1:随机端口，port=0）
    │
    ▼
data/medevidence.db/          ← 目录，不是文件
    collections/chunks/partitions/_default/data/*.parquet     ← 行数据
    collections/chunks/partitions/_default/indexes/*.autoindex ← HNSW 图
    wal/ · manifest.json · schema.json · LOCK
```

| 指标 | 实测值 |
|---|---|
| 语料 | 1,622 篇 PMC OA 全文 |
| 块数 | **26,230**（27,569 切出，过滤 4.9% 占位符） |
| 磁盘 | **252 MB**（向量 107 MB + 索引 105 MB + parquet/文本 + WAL） |
| **进程内存** | **696 MiB**（开库 + load 索引后；其中 pymilvus 自身 import 占 93 MiB），检索后 699 MiB |
| 开库 + load | **394 ms**（每进程一次，`search` 前必须 `load_collection`） |
| 单问检索 | embedding **297 ms** + 向量检索 **37.8 ms** ≈ **335 ms** |
| 写侧 | **单进程独占**：数据目录有 `LOCK`（Windows `msvcrt.locking`），第二个进程抛 `DataDirLockedError` |
| 多 worker | **不可用**：`uvicorn --workers 4` = 4 个进程抢同一数据目录 |

> 复现：`.\.venv\Scripts\python -m scratch.time_retrieval` / `scratch.mem_probe`（临时探针，第 4 周迁到 `src/eval/probe.py`）

### 1.1 部署到 2C2G 云服务器（第 4 周 v0）的内存预算

**实测服务器**（2026-10-25）：Ubuntu 22.04 / 2 vCPU / **内存 1608 MiB** / **无 swap** / 40G 盘（可用 27G）。

| 项 | MiB |
|---|---|
| 可用内存（`MemAvailable`） | 1094 |
| app 进程（pymilvus + 库 + 索引，实测） | −696 |
| OS + 系统服务预留 | ~150 |
| **余量** | **~250** |

**结论：能跑，但没有余量。** 无 swap 时 OOM killer 会直接杀进程，表现是「服务莫名重启、日志里没有 traceback」——这类故障最难查。

两件必做的事：

1. 加 **2 GB swapfile**（是保险，不是性能手段），`vm.swappiness=10`
2. 上真机后重测：`grep VmRSS /proc/$(pgrep -f uvicorn)/status`（Linux 有 page cache，可能略低于 Windows 的 696）

> 注：`store.close()` 之后 RSS 仍是 699 MiB —— 进程内的 Arrow / FAISS 结构要等**进程退出**才回收。
> 所以「用完就关」省不了内存，预算要按常驻算。

❌ **Milvus standalone 在这台机器上判死刑**：官方最低 8 GB，这台总数 1608 MiB，差 5 倍，不是"勉强"。
云端独立向量库的教学价值留到第 9 周**按量升配**（跑几天、练完降配），不为此换库、也不为此现在升配。

## 2. 容量账：什么时候必须迁

每篇 ≈ **16.2 块**；每块 ≈ **4 KB 向量**（1024 × float32）+ ~1.5 KB 文本。

| 规模 | 块数 | 向量 | HNSW 索引 | 判断 |
|---|---|---|---|---|
| 1,622 篇（现在） | 2.6 万 | 107 MB | 105 MB | Lite 完全够 |
| 1 万篇 | 16 万 | 648 MB | ~650 MB | Lite 勉强（2C2G 已不宽裕） |
| 10 万篇 | 162 万 | 6.6 GB | ~6.5 GB | **必须迁** |

**触发线（写死，不靠感觉）：**

- `chunk 数 > 50 万`，或
- `索引文件总和 > 机器内存的 50%`

理由：HNSW 图必须**常驻内存**才快；一旦超过可用内存开始换页，延迟从 ms 级掉到 s 级，而且表现为"时快时慢"，最难排查。

## 3. 瓶颈判定：不是向量库

单问链路拆开：**335 ms 检索 + 2–10 s 生成 → 生成占 85–95%。**

由此三条推论（这条比"要不要上 K8s"值钱）：

1. 横向扩容第一优先级是 **LLM 侧**：流式输出、结果缓存、并发限流、超时降级。向量库排在后面。
2. 这个量级下，Lite 单进程的检索能力（~3 QPS 顺序）**远没被摸到**，因为 LLM 那边先堵住。
3. 所以"上生产要换 standalone"的动机**是可用性与多副本，不是性能**。这个区分能挡住炫技式回答。

## 4. 上生产的 6 件事（按顺序，含验证方法）

| # | 事项 | 现在 | 改成 | 怎么验证 |
|---|---|---|---|---|
| 1 | 库的形态 | 进程内自动拉起 | 独立服务，`MILVUS_URI=http://host:19530` | 换 URI 后跑同一套 99 条测试 + 3 条探针，top-1 与本地逐字一致 |
| 2 | 应用状态 | 单进程，库在本机 | app 无状态、多副本；**写侧仍单点**（或走队列串行化） | 杀掉一个副本，检索不中断 |
| 3 | 认证 / 租户 | 默认无 auth | RBAC + database / collection 隔离 | 无 token 的请求被拒 |
| 4 | 索引 | `AUTOINDEX`（内部 FAISS HNSW） | 按量调参；建索引与写入解耦（先灌后建） | 灌 10 万块期间，检索 P99 不劣化 |
| 5 | 备份 | 拷目录，且**必须停写** | 快照 / 定期 dump + 版本化 | 从快照恢复后 count 与 top-1 一致 |
| 6 | 可观测 | 只有日志 | 空召回率、top-1 分数分布、P99、token 成本 | 大盘能回答"今天哪类问题问不出东西" |

⚠️ 第 **2** 项是唯一有真代码改动的：现在 `MilvusStore()` 默认在进程内开库，上生产后必须变成"连远端 + 失败重试 + 连接池"，这是接入层的事，不是表结构的事。

## 5. 明确不做（以及为什么）

- **不改表结构**：`pk / vector / text / pmc_id / section / chunk_index / path / source_type / text_hash` 在 standalone 上一字不用动。
- **不分片、不做多租户、不做冷热分层**：2.6 万块做这些是负收益。
- **不换向量库**（Qdrant / pgvector）：没有理由；Milvus 已经是全项目里迁移成本最低的一环。
- **不做本地模型部署**（vLLM / 量化）：见 `09` 第 11 条。

## 6. 三条现成话术

1. **"如果明天上生产要改什么？"**
   > 一个常量加五件运维、一件索引策略；表结构零改动。真正有代码改动的只有一处：应用不能再假设"库在我这个进程里"，得改成连远端 + 重试。我已经把这六件事和验证方法列在仓库的 `docs/production-path.md` 里。

2. **"QPS 多少？"**
   > 我的 QPS 不由向量库决定。实测检索 335 ms（embedding 297 + 向量检索 38），生成 2–10 s —— **生成占 85–95%**。所以扩容先扩 LLM 侧：流式、缓存、限流。

3. **"为什么现在不用 standalone？"**
   > 实测服务器可用内存只有 826Mi，standalone 最低 8GB 三容器；而且它默认不开认证、端口还对公网开放。这个量级用它是过度设计。迁移触发线我定在 50 万块或索引超过内存一半，到了再迁 —— 不是"以后再说"。
